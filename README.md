## 🛠️ Установка и локальный запуск

Требуется Node.js 22.18.0 (версия зафиксирована в `mise.toml`).

```bash
git clone https://github.com/maximusw124/ai-for-developers-project-387.git
cd ai-for-developers-project-387
npm ci
npm run dev
```

После запуска бэкенд доступен на `http://localhost:3000`, фронтенд — на `http://localhost:5173`.

Если используется mise:

```bash
mise run install
mise run dev
```

## Проверки

```bash
npm run check   # контракт, линтер, типы, сборка и тесты (эквивалент mise run check)
npm run e2e     # сквозные Playwright-тесты (эквивалент mise run e2e)
```

Заголовки коммитов и PR обязаны следовать **Conventional Commits** (правило в `AGENTS.md`); в PR его дополнительно проверяет workflow `PR title` (`.github/workflows/pr-title.yml`).

### Политика карантина нестабильных тестов

- Упавший в PR тест не перезапускается ради зелёного статуса; ретраи в PR запрещены.
- Если нестабильность подтверждена (падение в nightly без изменения кода или проход только со второй попытки), открывается тикет, а тест помечается `test.fixme(...)` с номером тикета — это карантин.
- В карантине тест остаётся видимым, но не блокирует PR. Возвращение в обычный прогон происходит той же правкой, которая закрывает тикет.
- Маскировать нестабильность ретраями, отключением трассировки или безосновательным увеличением таймаутов запрещено.

## 🤖 Автоматизация через OpenCode GitHub App

В репозитории подключён [OpenCode GitHub App](https://github.com/apps/opencode-agent) и воркфлоу `.github/workflows/opencode.yml`. Он позволяет вызывать агента прямо из обсуждения тикета или пулл-реквеста, включая комментарии к конкретным строкам diff.

- **События запуска:** `issue_comment` и `pull_request_review_comment` типа `created`. Первое срабатывает на новый комментарий к Issue или PR, второе — на комментарий к строке в PR. Другие события агента не запускают.
- **Команды вызова (mentions):** `/oc` и `/opencode`, например `/oc объясни этот тикет`. Команда распознаётся как отдельное слово: `/octocat` или `/ocnr` не срабатывают.
- **Допуск:** комментарий должен быть от OWNER, MEMBER или COLLABORATOR и не от бота. PR из fork не получают доступ к секретам: такой вызов отсекается до запуска агента.
- **Модель:** `opencode/big-pickle`. Ключ читается из секрета репозитория `OPENCODE_API_KEY` (Settings → Secrets and variables → Actions).
- **Назначение воркфлоу:** быстро разобраться в тикете, предложить правку или подготовить PR, сохраняя человека ответственным за финальное решение. Таймаут агента — 35 минут, предыдущий запуск того же PR не отменяется (`cancel-in-progress: false`).
- **Где смотреть результаты:** ответ агента появляется комментарием в Issue/PR; журнал, команды и ошибки — во вкладке Actions в запуске `opencode`.
- **Решение по `share`:** `false`. Репозиторий открытый, поэтому сессии намеренно не публикуются внешними ссылками; результаты остаются только в комментариях и логах Actions.

### Бюджет ручных вызовов на PR

- Лимит — **3 допущенных вызова модели на PR**. Значение по умолчанию задано в воркфлоу; при необходимости его можно переопределить переменной репозитория `AGENT_RUN_LIMIT` (Settings → Secrets and variables → Actions → Variables). Комментарии к Issue без PR в лимит не входят.
- Проверка делается в отдельной джобе `guard` **до** вызова модели. Источник счётчика — история GitHub Actions: `listWorkflowRuns` + `listJobsForWorkflowRunAttempt`. Учитываются только попытки с джобой `run_agent` (и историческим именем `opencode`), у которой `conclusion != skipped`; `success`, `failure`, `timed_out`, `cancelled` и незавершённые попытки считаются использованными. Текущая попытка пропускается, поэтому Re-run не даёт бесплатный вызов.
- У джобы `guard` есть только `actions: read`, `issues: read`, `pull-requests: read` и `contents: read`. У джобы с моделью нет прав `actions`, поэтому агент не может удалить или переписать историю запусков; OIDC (`id-token: write`) выдан только ей.
- При исчерпании бюджета модель не вызывается. Отдельная джоба `report` без модели публикует в PR комментарий со статусом «нужен человек», кодом причины, последним SHA и ссылкой на логи конкретной попытки.
- Возможные причины: `limit_exhausted` (бюджет исчерпан), `timeout` (таймаут агента), `infra` (сбой runner/инфраструктуры, включая отмену), `agent_failed` (ошибка самой модели). Комментарий публикуется только по этим причинам; обычные комментарии к Issue и успешные запуски его не получают.

### Автотриаж новых обращений

Отдельный воркфлоу `.github/workflows/auto-triage.yml` запускается на событие `issues` типа `opened` и делает предварительный разбор через скилл `triage`.

- **Допуск:** триаж запускается только для Issue от OWNER, MEMBER или COLLABORATOR и не от ботов.
- **Пропуск подготовленных тикетов:** Issue с меткой `ready-for-agent`, любым другим служебным state-лейблом (`needs-triage`, `needs-info`, `ready-for-human`, `wontfix`) или меткой `wayfinder:*` не разбирается повторно. Так тикеты, уже подготовленные скиллами `to-spec`/`to-tickets`, не попадают в автотриаж.
- **Параллельность:** `concurrency` группируется по номеру Issue (`auto-triage-${{ github.event.issue.number }}`), `cancel-in-progress: false` — уже идущий разбор не отменяется.
- **Таймаут:** 15 минут на джобу.
- **Границы агента:** изучает код и документацию, оставляет комментарий с предварительным выводом и уточняющими вопросами, обновляет метки трекера; код не меняет, коммиты, ветки и PR не создаёт.

### Независимое авторевью PR

Воркфлоу `.github/workflows/auto-review.yml` запускается только на `pull_request` (`opened`, `synchronize`, `reopened`) и готовит ревью отдельно от выполнения кода PR.

- **Допуск:** PR из этого же репозитория (`head.repo.full_name == github.repository`, не fork), автор OWNER, MEMBER или COLLABORATOR, либо доверенное приложение `opencode-agent[bot]` / `github-actions[bot]`. У ботов `author_association` обычно `NONE`, поэтому они допускаются по логину; PR из fork и другие боты ревью не запускают.
- **Разделение событий:** `issue_comment` и `pull_request_review_comment` здесь не используются — они остаются в `.github/workflows/opencode.yml` и срабатывают на комментарии с `/oc` или `/opencode`. Группы `concurrency` разные: `opencode-<n>` и `auto-review-<n>`, поэтому автоматическое ревью и ручной вызов агента не отменяют друг друга.
- **Подготовка:** обычный OpenCode CLI (`npm install --global @opencode/cli@2.3.2`, затем `opencode run --standalone --model opencode/big-pickle --file REVIEW.md`). Ключ берётся из секрета `OPENCODE_API_KEY`. Агент читает `REVIEW.md`, спецификацию, тикеты через `gh`, diff (`git diff $BASE_SHA $HEAD_SHA`) и результаты CI для head SHA через check-runs/statuses/actions; код репозитория не меняет, коммиты, ветки, PR, метки и комментарии не создаёт.
- **Публикация:** отдельная джоба с `gh pr comment ... --body-file -`. Токен с правом `pull-requests: write` доступен только ей; в джобе ревью у агента токен только для чтения. В `checkout` указано `persist-credentials: false`, OIDC (`id-token`) не запрашивается; после ревью проверяется, что рабочая директория осталась чистой.
- **Права уровня воркфлоу:** `contents: read`, `issues: read`, `actions: read`, `checks: read`, `statuses: read`, `pull-requests: write`. У джобы ревью нет права на запись PR, у джобы публикации — только `pull-requests: write`.
- **Устаревшие ревью:** `concurrency` по номеру PR с `cancel-in-progress: true` отменяет предыдущий запуск того же PR. Таймауты: 15 минут на подготовку, 5 минут на публикацию.
- **Критерии и формат:** [REVIEW.md](REVIEW.md). Комментарий содержит файл, строку, условие ошибки и последствие для каждого подтверждённого дефекта; если дефектов нет — явную строку `Подтверждённых дефектов по REVIEW.md не найдено.`. Вывод линтера (Biome) в ревью не дублируется — его проверяет `mise run check`.

Шаблон `.github/pull_request_template.md` требует ссылки на issue/спецификацию/тикеты/согласование и `Closes #N`, перечень запущенных команд со ссылками на прогоны и проверенный SHA, оценку риска по последствиям ошибки и способ отката, включая поиск данных при изменении миграций.

### Регулярный аудит по расписанию

Воркфлоу `.github/workflows/scheduled-audit.yml` раз в сутки запускает Lighthouse-аудит задеплоенного приложения и разбирает результаты агентом OpenCode.

- **Запуск:** `schedule` с cron `17 3 * * *` (03:17 UTC, 06:17 по Москве) и `workflow_dispatch` с опцией `demo_finding` для демонстрации учебной находки без реального дефекта.
- **Ограничения:** `concurrency` с группой `scheduled-audit` и `cancel-in-progress: false` — новый запуск ждёт окончания предыдущего; `timeout-minutes: 20`. Права: `id-token: write`, `issues: write`, `contents: read`.
- **Проверяемое приложение:** https://booking-app-5ssp.onrender.com (адрес берётся из переменной репозитория `APP_URL`; без неё аудит данных не выполняется).
- **Отчёты:** пишутся вне репозитория в `/tmp/audit-report/` — `report.json` (полные данные Lighthouse) и `summary.md` (компактная выжимка для агента). Директория загружается артефактом GitHub Actions `audit-report-<run_id>` (хранение 7 дней); в git-коммиты отчёты не попадают, а агент проверяет, что рабочая директория осталась чистой.
- **Вывод:** итог и логи агента фиксируются в прогоне (step summary и журнал джобы). По новой подтверждённой находке после поиска дублей создаётся отдельный issue со ссылкой на прогон и артефакт; при наличии дубля или отсутствии данных новый issue не создаётся.
- **Фактический прогон:** успешный [Scheduled audit #2 по расписанию](https://github.com/maximusw124/ai-for-developers-project-387/actions/runs/45112229742) (23 ноября 2026, ~1m 48s) создал [issue #11](https://github.com/maximusw124/ai-for-developers-project-387/issues/11) — 404 в консоли и возможности оптимизации Lighthouse.

## 🚀 Пользовательский сценарий (User Journey)

Ниже описан базовый сквозной сценарий работы сервиса: от настройки типа встречи владельцем до записи гостя и появления события в системе.

### Этап 1. Настройка типа встречи (Владелец)

1. Владелец переходит в раздел создания событий (**Event Types**) и нажимает кнопку создания нового типа встречи.
2. Заполняет основные параметры:
   - **Название (Title):** например, *«Консультация»* или *«30 Min Meeting»*.
   - **URL-слаг (Slug):** уникальный адрес для ссылки.
   - **Длительность (Length):** например, *30 минут*.
   - **Место проведения (Location):** выбор платформы для звонка (видеосвязь или очная встреча).
3. Сохраняет настройки — после этого создается публичная ссылка вида `domain.com/username/event-slug`.

### Этап 2. Запись на свободное время (Гость)

1. Гость переходит по публичной ссылке владельца.
2. В интерактивном календаре выбирает нужную дату и доступный временной слот.
3. Заполняет форму бронирования (указывает имя, email и при необходимости комментарий).
4. Подтверждает бронирование — отображается экран успешной записи (*Confirmation Screen*).

### Этап 3. Фиксация бронирования (Владелец)

1. Владелец открывает панель управления и переходит в раздел бронирований (**Bookings** -> **Upcoming**).
2. В списке появляется новая карточка встречи с данными гостя, выбранным временем и ссылкой на звонок. Занятый слот автоматически блокируется в календаре.

## 🌐 Развёртывание (Render)

Образ собирается из корневого `Dockerfile`: multi-stage сборка контракта, генерация API-клиентов, сборка фронтенда и бэкенда. Финальный контейнер запускает `node backend/dist/index.js` и раздаёт SPA и API с одного порта. Render задаёт переменную `PORT` автоматически, приложение слушает `0.0.0.0`.

### Подключение Render MCP без секретов в репозитории

`opencode.json` описывает удалённый MCP-сервер Render:

```json
{
  "mcp": {
    "render": {
      "type": "remote",
      "url": "https://mcp.render.com/mcp",
      "headers": { "Authorization": "Bearer {env:RENDER_API_KEY}" }
    }
  }
}
```

В конфиге нет ключа, токена и данных сессии: opencode подставляет значение из переменной окружения `RENDER_API_KEY`.

Шаги входа:

1. В Render Dashboard откройте **Account Settings → API Keys** и создайте ключ с доступом только к нужному workspace.
2. Задайте переменную в Shell до запуска opencode:
   ```bash
   export RENDER_API_KEY='...'
   ```
   либо в PowerShell:
   ```powershell
   $env:RENDER_API_KEY = '...'
   ```
   Не добавляйте значение в `.env`, который попадает в git.
3. Перезапустите opencode: конфиг читается только при старте. Проверьте соединение вызовом `list_workspaces`, затем задайте рабочий workspace (например, `Set my Render workspace to <name>`).
4. В редакторах с поддержкой OAuth (Claude Code, Codex, Cursor, Claude Desktop) можно войти через браузер без API-ключа: официальный Render plugin/connector, URL `https://mcp.render.com/mcp`. Для opencode используется вариант с переменной окружения выше.

### Хранение данных

Приложение использует SQLite по пути `/data/booking.db` (переменная `DATABASE_PATH` в образе). Без подключённого постоянного диска `/data` находится в записываемом слое контейнера: при перезапуске или редеплое сервиса данные удаляются. Чтобы записи сохранялись, подключите Render Persistent Disk к `/data` (доступно на платных планах) и оставьте `DATABASE_PATH=/data/booking.db` без изменений.

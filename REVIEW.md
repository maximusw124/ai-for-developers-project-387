# Критерии авторевью PR

Этот файл — источник критериев для независимого авторевью пулл-реквестов. Ревью дополняет, но не заменяет CI и не
изменяет код. Используйте термины из [GLOSSARY.md](GLOSSARY.md) и решения из [docs/adr/](docs/adr/).

## Что проверять

### Источники истины и границы ревью

- Сверять PR со спецификацией (`.scratch/booking-spec/spec.md`, `slices/`, `issues/`), тикетами в GitHub Issues
  репозитория `maximusw124/ai-for-developers-project-387` (`gh ... --repo maximusw124/ai-for-developers-project-387`),
  diff PR (`git diff $BASE_SHA $HEAD_SHA` либо `gh pr diff`) и результатами CI для `HEAD_SHA`
  (check-runs, statuses, runs workflow `CI`).
- Сообщать только о подтверждённых дефектах: утверждение должно опираться на код, спецификацию, тикет, тест или
  результат CI. Гипотезы, вопросы «на всякий случай» и общие пожелания не публиковать.
- Форматирование проверяет линтер (Biome) в рамках `mise run check`; дублировать его вывод в ревью не нужно.
  Не копировать в комментарий логи CI/тестов — ссылаться на прогон по необходимости.
- Не проверять и не предлагать то, чего в проекте нет по спецификации: отмену, удаление, изменение Расписания,
  ручную блокировку слота, статусы встреч, слоты произвольной длины и место проведения.
- Не изменять код репозитория: только чтение, анализ и подготовка текста комментария.

### Окно записи, Расписание и Доступность

- Окно записи — ровно 14 календарных дней Europe/Moscow, включая текущий день; каждый день присутствует в ответе,
  выходной или день без слотов отдаётся с пустым массивом `slots`.
- Рабочие часы: Пн–Пт 09:00–18:00 Europe/Moscow, шаг начала Слотов 30 минут; момент начала строго позже текущего
  времени; `начало + длительность <= 18:00`. Длительность берётся только из Типа встречи.
- Мгновения в API — ISO 8601 в UTC с `Z`; даты — `yyyy-MM-dd` в Europe/Moscow. Нельзя использовать локальную зону
  сервера или браузера для расчёта границ.
- Недоступные из-за Занятости слоты не должны появляться в Доступности; после успешного Бронирования слот исчезает
  из списка и для этого Типа встречи, и для других типов.

### Занятость, Конфликт слота и повторная запись

- Занятость — полуоткрытый интервал `[start, end)`: пересечение по правилу `busy.start < slot.end && busy.end > slot.start`.
  Примыкание (`busy.end == slot.start` или `slot.end == busy.start`) занятостью не считается.
- Занятость глобальна для всех Типов встреч и вычисляется только из созданных Встреч. Архивный тип встречи скрыт из
  публичной записи, но его существующие Встречи продолжают блокировать слоты в Доступности других типов.
- **Занятый слот не должен оставаться доступным для повторной записи.** Проверять оба уровня:
  1. `GET .../availability` не возвращает такой слот;
  2. `POST /api/bookings` на тот же интервал завершается `409 slot_taken` и не создаёт вторую строку в `bookings`.
- Проверять атомарность: проверка активности типа, корректности слота, пересечения и вставка должны происходить в одной
  транзакции; триггеры БД — страховка, а не единственная защита. При потере блокировки ожидается `503 service_busy`,
  а не тихая успешная запись или `409`.
- Невалидный слот — `422 slot_unavailable`; неизвестный или архивный тип — `404`; некорректный идентификатор — `400`.
  Отказ не должен создавать Встречу или оставлять частичные данные.
- При Конфликте слота на Странице записи: контакты сохраняются, выбранный слот сбрасывается, Доступность запрашивается
  заново, альтернативный слот не выбирается автоматически, фокус переводится на сообщение об ошибке.

### Соседние сценарии

- Длительности 30/45/60 минут и целый день (540 минут): последний допустимый старт и граница 18:00; интервал,
  заканчивающийся ровно в 18:00, корректен; старт позже — нет.
- Интервалы, примыкающие к уже занятым, остаются доступными; интервалы с частичным пересечением — нет.
- Границы суток и UTC: дата в Europe/Moscow не смещается при форматировании в UTC; проверять поведение в немосковской
  зоне (ночные прогоны с `TZ=Pacific/Kiritimati`), а также текущий день после 18:00 и в 00:00 по Москве.
- Предстоящие встречи включают идущую сейчас (`end_ms > now`), сортируются по началу, группируются по московской дате;
  ручное обновление списка не должно терять данные.
- Повторная отправка формы не должна создавать две Встречи подряд при отсутствии ответа сервера (идемпотентности нет,
  поэтому важны блокировка кнопки и защита на сервере).

### Контракт, тесты и CI

- Изменения API отражаются в `contract/main.tsp` и снимке `contract/openapi/openapi.yaml`; снимок не должен расходиться
  с генерацией (`check:contract`).
- Критичные сценарии покрыты тестами: доступность и геометрия слотов, успешное Бронирование, исчезновение слота,
  `409`, триггеры БД, гонка за один слот (`503` + ровно один успех), соседние интервалы, архивный тип.
- PR не должен ослаблять проверки: ретраи в PR, `test.fixme` без тикета, отключение трассировки и необоснованное
  увеличение таймаутов недопустимы (политика карантина в README.md).
- Мутационная проверка `mise run test:broken-conflict` и гонка `bookingRace.test.ts` запускаются в nightly; в PR
  достаточно убедиться, что защита от пересечений не была удалена или обойдена.

## Формат замечаний

Комментарий начинается со строки `> *This was generated by AI during automated review.*`, затем идёт список.
Каждое замечание — одна строка со всеми четырьмя элементами:

- `<путь к файлу>:<номер строки>` — **Условие ошибки:** ... **Последствие:** ...

Путь и строка должны указывать на место из diff PR или на строку исходного файла, где возникает дефект. Для дефекта
спецификации укажите файл из `.scratch/booking-spec/` или этот файл. Одно замечание — один дефект.

Если подтверждённых дефектов нет, комментарий состоит только из заголовка и строки:

`Подтверждённых дефектов по REVIEW.md не найдено.`

Запрещено добавлять разделы с неподтверждёнными рисками, вопросами, копиями вывода линтера, тестов или CI, а также
предлагать правки кода в комментарии.
